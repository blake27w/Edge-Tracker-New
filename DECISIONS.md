# Edge Tracker — Decisions

Append-only. Newest at the bottom. Format: `D<n> (YYYY-MM-DD) — decision — why`.

- D1 (2026-07-05) — `~/Edge-Tracker-New` is the canonical repo; `~/edge-tracker/` and Desktop copies are archived — it's the GitHub-synced tree with the latest work (PR #120, 2026-07-03).
- D2 (2026-09-16) — Learning-loop bundle landed as direct commits to `main`, not a PR — Blake asked for push-to-main explicitly; CLAUDE.md's branch/PR norm still stands for future work.
- D3 (2026-09-16) — `scripts/migrate-research.sql` lives in the repo rather than only in the delivery zip — the schema the new agents depend on should be reconstructible from the tree alone.
- D4 (2026-09-16) — History agents read closing lines from ESPN's **core** API (`sports.core.api.espn.com/.../competitions/<id>/odds`) when `site.api`'s `pickcenter` is empty, and skip any provider whose name matches `/live/i` — ESPN empties pickcenter for older games (the key stays, the array goes to `[]`), which is why nfl-history graded only 124 of 588; the "Live Odds" entries are in-game snapshots that would poison totals (ORE/MSU 2024: 52.5 close vs 39.5 live).
- D5 (2026-09-16) — History agents distinguish "no line on record" from "fetch failed", and never cache a failed fetch — a transient error used to poison that game for the life of the process.
- D6 (2026-09-16) — Football gets priority Sep–Jan via **two** mechanisms, both keyed off `FOOTBALL_PRIORITY=auto|true|false` (auto = Sep–Jan, evaluated per call so a long-running process crosses months): (1) NFL/NCAAF stay in the per-sport **ceiling** denominator all season even with no slate on the board; (2) their unspent credits form a **floor** non-football sports may not spend into — the allocation shares are ceilings and spend is sequential, so a share alone never protected football. In Sep 2026 MLB+soccer drained the 20k by day 15 while NFL had used 1064 of ~7450. The two are not redundant: ceilings stop other sports *earning* an inflated share (football's 0.48 leaving the denominator inflated soccer's cap to ~2040 vs ~700), the floor stops them *spending* football's remainder.
- D7 (2026-09-16) — Odds budget is the real constraint, not agent coverage: 19915/20000 used by day 15 (pace ×1.99), which is why ~30 agents reported "no games on the slate". Fixes above take effect at the Oct 1 reset; `ODDS_SKIP_SPORTS=SOCCER,WNBA,BOXING` alone is only ~12% of spend and was never going to close a 2× overrun.
- D8 (2026-10-14) — Agents get a shared **degradation channel** (`reportDegraded`/`getDegraded` in `src/store`, folded into the watchdog as `type: 'data'` issues and onto `/health.system.degraded`) — the orchestrator marks a run failed only when it *throws*, so all four faults found today sat behind a `catch (_)` or a silent `continue` and reported `status: idle`, `0 errors`, `0 consecutive failures` indefinitely. "Succeeded while producing nothing usable" had no way to be expressed; now it does, and entries self-expire (90 min default) so a fix clears the alert without anything having to remember to.
- D9 (2026-10-14) — CLV's closing snapshot is fetched with a **descending** query bounded to **pre-kickoff** rows, and the entry batch is the last batch *at or before* `scored_at`. Root cause of "0 beat close, 20 suspect": the query was `order fetched_at ASC, limit 1000`, and one game/market/side accumulates ~8 rows per poll, so 1000 rows is only ~6h of a game that sits on the board for a week — the real close was truncated away, the play was scored later than every row returned, the "nearest" entry batch *was* the last one, and `suspect = !(close > entry)` flagged everything. Verified by running old and new code over the same 1600-row fixture: old reported `close_at` 12.5h early and `entry_at === close_at`. The pre-kickoff bound is the same hazard D4 found in the history agents (a live in-game number read as a close) — here it would have fabricated CLV that `done` then locked in permanently.
- D10 (2026-10-14) — `beat_close` is **nullable** and price-aware: `clv` (line points) plus `clv_odds` (points of implied probability), with price breaking a flat-line tie and `null` when neither is knowable. On a spread or total that didn't move, line-only CLV scores every bet as "did not beat the close" even when the price on that number improved — which is most of a spread/total record, and is why the reading was pinned near 0%. Unknowns are excluded from the `beat_pct` denominator rather than counted as misses, in **all four** consumers (dashboard, `backtest`, `clvByMarket`, `digest`) — fixing only the dashboard would have left the digest emailing a contradicting number. Also fixed `batchConsensus`: `Number(null)` is `0` and `0` is finite, so a missing price became American odds of `0` and dragged the median.
- D11 (2026-10-14) — The grading queue is **windowed** (`GRADE_LOOKBACK_DAYS`, default 10), ordered **newest-first**, restricted to gradeable sports **in the query**, and plays older than the window are retired to `status: 'expired'`. Root cause of `graded 0` across 868 runs: the pending select had an upper bound but no lower bound and took `limit: 80` *oldest*-first, so once 80 never-gradeable rows accumulated they held the head of the queue permanently and no newer play was ever reached. `opp-grading` never hit this because it windows on a 30h lookback — which is why it graded 187 rows the same day. Reproduced against the old code: a fresh, gradeable play plus 80 ancient ones → `graded 0 (0W-0L-0P)`, the exact production string. `expired` sits outside the win/loss/push record so no reported number moves; `dedupe()`'s keeper election was changed to prefer `pending` over `expired`, or a rescheduled game's fresh row would be deleted in favour of its retired one.
- D12 (2026-10-14) — `/data-health` reports its own query failures (`queryErrors[]`, a per-row `error`, HTTP **207**) and distinguishes a **missing table** from a **failed query** via PostgREST error codes. The `line_snapshots` nulls were a count timing out inside `catch (_) { /* table optional */ }`, and `errorsToday` only counts agent `scan_runs` rows, so an endpoint-level failure appeared nowhere. A no-DB response now says so instead of answering 200 with a wall of nulls. Degraded payloads are cached only ~10s so one transient timeout can't pin the endpoint to 207.
- D13 (2026-10-14) — `/data-health`'s 36s came from **23 sequential exact counts over unindexed timestamps**: every counted table had its timestamp only as the *trailing* column of a composite index, which Postgres can't use for a bare `ts >= midnight` filter, so even the "today" counts were full sequential scans. Fix is three-part — single-column timestamp indexes in `schema.sql`, planner-estimate (`count: 'estimated'`) totals for the big append-only tables while "today" stays exact, and all counts in one concurrent wave behind a 60s cache. Measured 303ms for 23×150ms counts that would be ~3.5s serially.
- D14 (2026-10-14) — Every new alarm carries a **sample-size floor** (`CLV_ALARM_MIN` 12, `GRADE_ZERO_ALARM_MIN` 5) and the grading alarm additionally requires that **ESPN actually returned finals** for the play's sport+date. Plays are logged up to 36h before kickoff while the grading cutoff is only `scored_at - 3.5h`, so "queued but 0 graded" is the *normal* state of an afternoon run; alarming on it would have sent a false alert every day, and an alert that cries wolf is worth less than no alert. The per-stage counters still appear in every summary unconditionally — the counters are the diagnosis, the alarm is only for when it's provably our bug.
- D20 (2026-10-17) — **The repo has a test suite now** (`edge-tracker-agents/test/`, `npm test`), built on `node:test` + `mock.module` with **zero new dependencies** and **zero production refactoring** — the only `src/` change in the whole suite is one `export { capture }` line. That constraint was deliberate: PR #130 is awaiting review, and widening its reviewable diff with a testability refactor would have made it harder to merge, not easier. 34 cases covering all five faults. Needs Node 22.3+ for `--experimental-test-module-mocks` (the app still only needs 20; Railway runs `node src/index.js` and never sees the flag).
- D21 (2026-10-17) — The suite was **mutation-tested rather than assumed**: reintroducing each original bug one at a time — the ascending+`limit: 1000` close query, grading's missing lower bound, scoring an unknown close as a miss, and re-swallowing the data-health count errors — fails 1, 1, 1 and 5 cases respectively. A suite that passes against the broken code is worse than none, because it licenses the belief that the fix is guarded. Worth re-running this way after any change to these paths.
- D22 (2026-10-17) — Tests assert on **query shape**, not only on returned rows: ordering direction, the presence of a lower bound, the count mode. Three of the five faults were query-shape bugs that returned perfectly valid-looking data, so a test checking only results would have passed against every one of them. `helpers/fake-db.js` records every call for exactly this. Same principle for failures: assert they reach ERROR level and the degradation channel, not merely that nothing threw — "it didn't crash" was true of all five faults.
- D23 (2026-10-17) — The CLV close-selection fixture deliberately seeds **1600 snapshot rows** (200 polls × 8 books) for a single game/market/side. Below ~1000 the old code behaves correctly, so a smaller fixture passes against the bug — the fault was invisible at test-sized data volumes, which is most of why it survived. If that fixture ever gets "simplified", the test stops testing anything.
