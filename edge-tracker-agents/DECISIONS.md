- D15 (2026-10-14) — **`schema.sql` has been un-runnable since 2026-07-03** and that is why every migration since has been "owed". `freeze` is a *reserved* keyword in Postgres, so `alter table public_splits add column if not exists freeze boolean` (added by #123, `960556e`) is a syntax error. In the Supabase SQL editor the whole script runs in one transaction, so that single line aborted and rolled back everything — including the September work and the D12/D13 indexes. Verified by applying the file to a real Postgres 16: it failed at line 760 and now applies clean and idempotent. Column quoted as `"freeze"`; PostgREST quotes all identifiers, so no agent code changes. Corollary worth remembering: `last_update` (#96, 2026-06-23) *is* in production because it predates the break — the dividing line is 2026-07-03, not "the last thing we added".
- D16 (2026-10-14) — **Fifth silent fault, found while fixing the migration: `public_splits` inserts have failed for 103 days.** The agent writes `freeze`/`pileon`/`net_move`, D15 means those columns never existed, and the insert is `catch (e) { logger.warn(...) }` — so it reported `3 splits · 2 freeze` with 0 failures while `/data-health` showed `public_splits: today 0, total 671` (671 being the pre-#123 total). This is precisely the "today: 0 on an in-season table" tell `/data-health` was built for, sitting unread in the payload. Nobody had looked.
- D17 (2026-10-14) — Failed **writes** are reported from `src/db` itself, not from the 92 agent call sites that swallow them. Every agent wraps DB writes in `catch (e) { logger.warn(...) }`: a warn doesn't fail the run, so an agent whose entire output failed to persist still reports success, and patching 92 sites would be a far larger and riskier change than fixing the one layer they all go through. `insert`/`upsert`/`update`/`del` now call `reportDegraded('write|<table>', …)` and **rethrow unchanged** — no control-flow change, pure observability, and it distinguishes "schema out of date" from other failures. Any future instance of D16 surfaces on its own.
- D18 (2026-10-14) — The `/data-health` indexes ship **twice, deliberately**: plain `create index` in `schema.sql` for a fresh database, and `create index concurrently` in `scripts/migrate-data-health-indexes.sql` for an existing one, to be run **first**. A plain `create index` takes a SHARE lock that blocks inserts for the whole build — verified against a real server — which on production `line_snapshots` means the odds agent silently drops snapshots and corrupts the very CLV data D9/D10 just fixed. `concurrently` cannot run inside a transaction block (also verified: `ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`), and the Supabase SQL editor wraps multi-statement scripts in one — which is exactly why it cannot live in `schema.sql` and needs psql or statement-at-a-time execution. My first cut of D13 had only the blocking form; shipping it as-is would have caused an outage in the system it was meant to instrument.
- D19 (2026-10-14) — D13's premise is now **measured, not reasoned**: on a 400k-row `line_snapshots` with both pre-existing composite indexes in place, the `today` count planned a **Parallel Seq Scan at 16.2ms**; with `(fetched_at desc)` added it plans a **Bitmap Index Scan at 3.9ms**. The seq scan is O(table) and the index scan O(matching rows), so the gap widens with size — production is large enough that the exact `count(*)` times out. `reltuples` returned exactly 400000 for free, confirming `count: 'estimated'` as the right call for the big totals.
